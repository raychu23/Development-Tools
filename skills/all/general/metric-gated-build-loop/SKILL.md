# Metric-gated build loop

Use when the user says to start building with goals, checkpoints, metrics or benchmarks as the loop goals, or whenever several ledger tasks should run against measured targets. Each task runs produce → check → correct until green, against checks committed before its code; "done" stays a claim until checks the builder didn't write and can't change pass, with the evidence saved. Task states and commands follow the `ledger` skill, launching chats follows `spawn-agent`, and a single fix that already failed twice follows `fix-loop-metric-gate`.

For a single hard or long task without ledger tasks, use the lighter `goal-metric-loop`; this skill is the multi-task, builder-chat version of the same shape.

## 1. Targets from the plan

- Take the targets from the user's plan (a plan page, a resume written as the plan). Keep them ambitious and make each defensible by giving it a task and a metric, never by trimming it to what's already proven.
- Every target is a number with its baseline: what outside tools scored on the same key, the current value, or a published reference point. Reuse an existing frozen answer key (an earlier tool trial's) so new scores compare with old ones.
- A head-to-head baseline must do the same job on the same unit. A tool built for another granularity (git's file-rename detection vs functions renamed inside a file) scoring 0% is a strawman: keep the row for honesty but mark it "not a fair comparison, don't cite" so resume and pitch pages never quote it.
- The baseline is the strongest thing a team already has for that job, not a weak store you invent: "latest-only" loses to git history for as-of questions, so git history is the baseline. A baseline you reimplemented from a vendor's docs is labeled "<vendor>'s documented method", never the product's name.
- The key must exercise the feature's distinguishing part: a bitemporal bench whose questions all have valid time = record time never tests the second clock. Add questions only that part can answer (backdated, corrected) before claiming it.
- Small n: report every metric as "k of n" with its 95% Wilson interval in the scoreboard and loop report. On n ≤ 20 a one-case miss is inside the noise (17/20 = 64-95%), so either grow the key to ≥ 50 or run pass^k before calling pass or fail; only results with large n (e.g. 136/136, 0/1151) support a bare "100%".
- Pick metrics bottom-up when the feature acts on agents or people: read real traces first (open coding → group the failures → count), then make the top failure groups the metrics. Metrics chosen top-down from the design measure what was easy to build.
- Score the product as what it is. A checker/verifier is scored like one (catch rate, precision, false-alarm rate) against the other ways teams verify the same thing (an LLM reviewer given the same records, rule linters, search-based review), at equal catch rate, with cost and latency per check and the one-time capture cost (model drafting + human approval) included. Comparing it to "RAG answering anything" is the wrong job, and the user rejects it as unfair.
- Don't hand a baseline the product's own job. An LLM reviewer given "the governing decision" has had the routing done for it (the part Mole exists to do), so beating or losing to it measures the check alone. Keep that arm as the ceiling, and make the headline comparison against what a team would really run without the product (an LLM given ALL decisions / RAG), with a product arm that does its own routing and reports routing accuracy.
- Resume metrics: the user wants 2, dense, each the field's metric vs a named alternative. Open-ended QA scores ("can the agent answer why") read as not rigorous to him: keep them as internal acceptance checks, not resume lines. Cost/speed only counts as a standout when measured against the alternative at the same accuracy. Compute cost from tokens per check, never from call counts: batching escalations into one call cut calls ~40% but cost ~4%, because the text sent dominates.
- A resume bullet for a feature with no code (staged rollout vs holdout) stays a target with X/Y; say so before anything else. The fastest real number for its "before code" half is a historical backtest. Take real merged changes and label each with a rule fixed before the run: "failed" = reverted, or traced as the cause of a fix within 30 days (SZZ); "stuck" = neither within 90 days. Run the product's check on each change against the records as they stood at its parent commit, and score the share of later-failed changes flagged before merge plus false alarms on changes that stuck. Split dev/held-out by time and run the same baselines. Scope the claim to changes that touch a recorded decision. Keep DORA change-failure-rate wording until a real rollout runs.
    - Fit-check before the full run (minutes, not hours): run the product's check on 5-10 of the "failed" changes first and read what each revert fixed. In a mature repo most reverts are ordinary bugs (UI, CI, build) that break no recorded decision, so a decision checker correctly flags ~0 and the rate X → Y doesn't move (X ≈ Y). Then say the CFR wording can't be supported and switch to a decision-related outcome (review comments citing a decision that the check would have raised first, or the proposed-change catch rate).
    - X (failed ÷ merged) is just counting; Y needs the product run on every failed change. Report them separately when the user asks for it "quickly".
    - Finding reverts: GitHub's revert button merges a branch named `revert-<PR>-…`, so on first-parent history grep merge subjects for `revert-<digits>` and map back to `Merge pull request #<digits>`; the "This reverts commit" body line alone misses most of them.
- For a checker that must first pick which records apply, report routing accuracy as its own metric: it is the recall ceiling (a record the router never selects can't be caught), and it tells you whether to fix capture (scopes, anchors) or the check itself.
- Credible-suite checklist (what interviewers ask): key + protocol frozen and hashed before any arm · held-out split reported once · strongest real baseline as shipped · n + Wilson/bootstrap 95% + wins/ties/losses · one-change-at-a-time ablations · ~20% of AI-judge grades re-graded blind by people (κ) · cost + latency beside accuracy · ≥ 3 repeats. Write the missing ones into the results page instead of hiding them.
- A pre-registered protocol whose arm is shown obsolete before it runs (the mechanism it tests was replaced) is never edited: write protocol vN+1 as a new pre-registration citing why, keep the old frozen file, interleave arms in the new run (arms run on different days are confounded), and size an overnight run as a pilot with its minimum detectable effect stated.
- Launch-readiness review before a long scored run (a fresh reviewer, before any scored row exists):
    - count which tasks can exercise the mechanism at all (e.g. only tasks whose gotcha a crisp rule covers). Pooling over tasks that can't differ dilutes an underpowered pilot to nothing, so make mechanism outcomes on those tasks primary (violations left at the end, block-fire rate, fix-after-block rate) and spend most epochs there, with the pooled comparison secondary and descriptive;
    - open the scorer the runner actually calls, not the one the protocol text names: a fix landed in one adapter while the runner still called the old scorer that ignores new files;
    - pin the product as its shipped artefact (the packed tarball installed in the run's scratch, sha256 + source commit in the protocol and every run record) so merges during the run can't change it;
    - make the freeze file pass the tool's default `--check` invocation. Changes now are a re-registration (new file, own hash), not a deviation;
    - exclude every arm's setup files (the product's record folder, CLAUDE.md/AGENTS.md) from the scored diff, identically for all arms: they show up as new files in one arm only and can match grep-based checks.
- Before powering a comparison of a mechanism that fires on a mistake (blocking, a judge), pre-register a small no-context base-rate run with its decision rule written in advance (e.g. upper Wilson bound < 20% → the benchmark can't test it, build seeded traps). A pilot where neither arm makes the mistake says nothing for or against the mechanism; report it as "never exercised", not as a tie.
- A test where no arm separates from "no context at all" (all within noise) can't measure team memory, because the model already knows the common answers; demote it rather than tuning to it. A gain seen only on the cases you adjusted on is not a gain until held-out shows it.
- With-vs-without tests must use the product's real output (hook text, MCP reply captured verbatim). A hand-written hint that names the fix is an upper bound only, and with ≤ 3 distinct tasks the runs are not independent: report effective n = distinct tasks.
- Agent-regression tasks must be break-prone: pilot each with the no-product arm (2 runs, never scored) and keep only tasks broken ≥ 1/2. Plain coding tasks rarely break anything because the agent runs the guarding unit test itself; tasks that tempt an architectural shortcut caught only by a decision rule (layering, read-only module, import boundary) do. Compare context before the edit with a check after the edit + one retry as separate arms: the pre-edit hint alone can leave behaviour unchanged while the post-edit loop prevents the break. Report task-done rate, time and cost beside the regression rate, since the retry costs ~2-3×.
- A headline number re-run on a fresh, bigger set (new repos) that drops sharply must not be cited, old or new, until explained. If the baselines collapse on the same new split too (an LLM given all decisions falling from 100% to 24%), suspect the harness or the new repos' records first (missing scopes, records not loaded) and check routing accuracy per repo before calling it a product loss.
- User wants a first result within a deadline while a long run builds: steer the runner to freeze and score a first batch as soon as the minimum is ready (e.g. ≥ 3 piloted tasks × 5 epochs), write partial results first, and add later cases as a second frozen batch; never unfreeze to add cases into a scored batch.
- Circular keys: if the answer key comes from the same engine the code calls (go-to-definition = the TypeScript language service = the compiler Mole uses), 100% proves "it asks the engine", and a competitor on the same engine losing by a few points is edge cases, not a design win. Say so in the scoreboard row.

## 2. Goals file before any task

Commit `tasks/loop-goals.json` in the code repo:

| key | holds |
|---|---|
| asked | the user's request, verbatim |
| loop_rules | R1–R7 (section 4), so builders read them from the repo |
| end_goals | E#: the outcome in plain words + `measured_by` metric ids |
| metrics | M#: name, how it's computed, target with baseline, owning task |
| benchmarks | B#: what + path |
| graph | task + needs (an edge only where a task reads another's output) + why |
| checkpoints | C#: when + pass (metrics at target and reviewed; a dogfood run on the repo's own recent changes; a report written) |
| never | non-goals every task inherits |

Add `tasks/loop_status.py`. With `--check` it fails on a missing key, an end goal naming an unknown metric, a metric whose task isn't in the graph, a missing benchmark path, a graph task with no ledger folder, or `needs` naming an unknown task; mutation-test that once. Without flags it prints each task's ledger state and its latest metric value from `runs.jsonl` next to the target. Run it as `python3 -B` so no `__pycache__` lands in `tasks/`.

Never point a benchmark path at `~/.hermes/cache/scratch` (TMPDIR): entries idle 24 h are pruned, the status script then reports the goals INVALID, and every page renderer that quotes its numbers fails. Keep benchmark clones in a durable cache dir (e.g. `~/.hermes/cache/<project>-bench/`); on a tight disk copy an existing clone with `cp -cR` (APFS clone, near-zero space), confirm the commits the results cite exist, then update the path in the goals file.

Benchmarks in untracked or ignored folders don't exist inside a ledger worktree. Resolve their paths against the main checkout too (`git rev-parse --path-format=absolute --git-common-dir`, then its parent), and have builders copy what a bench needs into the package's `bench/` in the checks-first commit. The reverse: a builder's edits to an ignored folder inside its worktree (runner scripts under a gitignored `context/`) never reach main by merge. Before launching from main, diff those files against the worktree copy and check the frozen hashes; run from the worktree copy (keep the worktree until analysed) rather than overwrite main's copy another frozen protocol hashes.

## 3. Tasks

- `ledger new <abs path>/tasks <name>` with every contract field, then `ledger move … ready --owner <chat>`. Done-when = numbered checks: the metric target, one failure or empty case, the repo's full check. `--checks` = the exact bench command.
- A task the user hasn't approved stays `proposed` with its decision open; builder chats only take `ready` tasks. List proposed tasks in the goals file's `proposed_next` (task · "proposed, waits for D#" · metric · why) so the queue is visible in status without being claimable.
- Paid or account-bound steps go in non-goals: build the harness and a tiny dry run; the full run waits for the user's go.
- Every user-facing feature's done-when names the surface where the user meets it (an editor view section, hover, file-tree badge, Problems diagnostic, command, agent hook) and checks it in the real product (a DOM dump or screenshot from a real window). A backend task with only a CLI ships invisible: the user asks why it's in the terminal and not the panel. Give the surface work to one builder that owns the extension, and have backend tasks publish a JSON contract (in their goal) that the surface reads when present.
- Every feature's UI text and README line say what it does for the product's center (e.g. the decisions behind the code), and an integration says what it adds over the closest existing tool of its kind. Otherwise the user can't see the point of each part.
- Proposed → ready for a run nobody watches:
    - fill every empty contract field (boundary with exact package paths, checks with the exact bench path, non-goals, proof, stop). Proposals are often written with goal + done-when only.
    - rewrite each done-when item that needs people, a push or paid spend into a local proxy plus a kit left for the user, e.g. fresh subagents with vs without the feature instead of a junior study, or the workflow's steps run locally instead of a timed push. Otherwise the builder blocks on it.
    - give tasks that build on each other one shared package, so later tasks don't edit another task's files mid-run.
    - in the same turn, add their metrics, graph edges, end goals and a checkpoint to the goals file, drop them from `proposed_next`, and run `loop_status.py --check`.
    - Reassigning a blocked task (`ledger move … ready --owner new`) keeps the old `owner:` line, and so does a claim with `--worktree`. Set the `owner:` field in its `0 start.md` by hand and commit it, or the agents board credits the task to the old chat.

## 4. Loop rules (in the goals file and every brief)

- R0 prior art first (prior-art-first skill): before the checks-first commit, `tasks/<T>/4 log/prior-art.md` names the standard approaches for this exact problem (papers, open-source code, vendor docs, recent blogs, benchmarks; pages saved with URL + date), the method picked and why, and how the field measures it. The bench uses the field's metric and bar where one exists. A reviewer rejects a bench or method without it. It exists because hand-picked thresholds and guessed matching rules look fine on the key they were tuned on and then miss the target.
    - Integrate, don't build alone (the user's repeated rule): build ON the established open-source stack (an eval harness such as Inspect AI, standard record formats, the host tool's own contract like Claude Code hook block/deny) and write only adapters + the gap, in native formats so the ecosystem's viewers and installers work, usable by the product's users inside tools they already run (CI, hooks, MCP clients). Every brief names the user's take-vs-build design docs and requires citing the section followed; a brief that allows "our own small package if reuse doesn't fit" invites the wrong build.
- R1 checks first: a task's first commit is the bench, its key (dated) and failing tests, nothing else.
- R2 can't change: the implementer never edits them; a needed change goes to `tasks/<T>/4 log/key-changes.md` with the reason and a repro, then a fresh subagent rules in `4 log/key-ruling-N.md` (APPROVE with the exact allowed edit, or REJECT with what the code must do instead) and the implementer applies only that edit, citing the ruling in a comment. Don't block on it: the builder keeps going around the disputed item meanwhile. A test's wall-clock budget (vitest's default 5 s) is not an acceptance criterion unless the contract names a speed, so a ruling may raise it for a test that times out under outside load; first cut the real cost (lazy imports) so the raise isn't hiding a slowdown.
- R3 repeat until green, at most 6 rounds; the same failure 3 rounds in a row → `ledger move … blocked` with the cause.
- Triage every `blocked` the same turn you see it; never report "blocked" to the user as an end state. Sort each one: (a) the task's own metric passed but the full check failed on unrelated tests (timeouts while many builders load the host) → a shared test-infrastructure bug: fix it once on main in its own small commit (raise `testTimeout`/`hookTimeout`, cap worker threads/forks), prove the full check green twice, then unblock and integrate all such tasks; (b) a real metric miss → a fresh builder with the previous owner's diagnosis, ≤ 6 rounds, then integrate at the real number with the claim changed (R7) only if 0 false verdicts on planted defects. Builders re-block task after task on a shared cause they don't own, so one fix unblocks several.
- R4 evidence: every check run appends `{"time","commit","cmd","exit","metrics":{"M#":…}}` to `tasks/<T>/4 log/runs.jsonl`; a wrong line is corrected by a new line saying so, never edited.
- R5 fresh reviewer: a subagent given only the contract and the diff, never the builder's transcript; test diff first; P0–P2 findings, each with a reproducer; at most 2 rounds.
    - Brief the reviewer with the specific risk you suspect ("esbuild can't bundle a non-literal import", "a stale index hides violations", "the hook writes the real file"), and require attacks that run the shipped path: the installed tarball, the action as a third-party repo, a SIGKILL mid-hook. Builder summaries and their tests repeatedly passed while those paths broke. Every step the builder marked NOT RUN (real-window proof, package + install, full check) goes first in the reviewer's brief, before any attack, so the merge decision never rests on a skipped proof.
    - "Built on <library>" is a claim: the reviewer greps for the import and runs the library's own entry point (`inspect eval`, its viewer). Prose and docstrings naming a framework the code never calls is the home-grown build the user rejects.
    - A fix round may introduce a new HIGH (a per-file subprocess loop, a regex that rewrites code): every fix round gets its own fresh review, and a narrow verified fix can be re-checked by rerunning its tests yourself.
    - Attack every "installed / ready / fresh" signal for silent degradation: run the check where the agent or user actually runs (inside the sandbox, on a fresh `git clone`, in a linked worktree), and make it test the FEATURE, not presence. A preflight that only proved the CLI resolved passed on a release older than the feature under test; an mtime staleness check flagged every CI checkout; an exclude written via `--git-dir` missed linked worktrees. A fallback is fine only if it warns and is recorded in the run's metadata.
    - A hand-written lexer/parser of a real language (statement starts, import resolution) gets a differential oracle before the next review round, not more hand-picked edge cases: the language's own tokenizer (CPython `tokenize`) as truth, run on a whole real corpus (stdlib incl. its test dirs + installed packages) plus a grammar fuzz of `ast.parse`-valid files, rerun after every fix. Reviews otherwise find one construct per round (comment brackets → backslash-continued strings → PEP 701 f-strings), and a fix for one construct silently regressed another that only the corpus caught. Commit the oracle scripts in the task log so reviewers rerun them.
    - New defaults must reproduce the old behaviour on an in-place upgrade (queue names, config keys, file layouts): a namespacing default derived from the DB name silently orphaned already-queued jobs while the docs claimed "no migration". Make the new behaviour opt-in and test the upgrade itself (state written by the old version is still processed after restart with the env unchanged).
    - A test named after a regression must fail on the pre-fix code: prove it with the old function swapped back in, 5 runs each way, saved to the task log. For "the server stays responsive" use a slow fake binary on PATH (sleeps, then execs the real one) plus a `setInterval` heartbeat asserting the max gap, with a wide margin; a thin-margin wall-clock percentile flaked half the time and also passed on the blocking code.
    - A builder's "the library can't do X" (no bucket/View API, no concurrency option) or "the upstream tool doesn't emit X" is a claim: check the installed package's own type definitions, and for a data format check that OUR decoder's generated schema matches upstream's current one (a decoder generated from an older proto silently drops new fields into unknown-fields, so the tool looks broken). Excused gaps were repeatedly available in the installed version or lost by our own stale reader.
    - Your own fix for a finding can break a contract the reviewer never tested, so run the full check before merging it, not just the new test. A gc-safety fix that pinned refs in the user's repo broke "the hook leaves the repo untouched" (refs show in `git log --all` and travel with `git push --mirror`). Product caches and helpers must create no refs, branches, tags or registered worktrees in the user's repo; prefer a cache that self-heals (rebuild the slot when its object is gone) and test that no refs appear. A cache stored under `.git/` is invisible to most tools, but any config whose exclude list REPLACES the defaults (vitest `test.exclude`) must restate `**/.git/**`, or the suite collects the cached checkouts.
    - A narrow, reproduced finding (one function, one wrong flag): fix it yourself tests-first (red saved, then green) instead of another builder round, then still send a fresh narrow review of just that commit. Broad findings go back to a builder with the review log path.
- R6 metrics are computed by code; a model may only reword facts code found.
- R7 green only through implementation, never by loosening a check. A missed target changes the claim built on it, not the metric.

What the builder brief must also say:
- Key independence: the key's truth comes from a different method than the code under test (line ranges from `git diff -w` vs the implementation's normalized-body hash; hand-written expectations from the fixture definition), pinned to exact shas, and frozen in the red commit. A key generated by the implementation only confirms itself.
- Held-out keys for anything tuned: thresholds or options picked after seeing the frozen key overfit it. Label at least one held-out key (another repo or other history) before any score, score every option on the frozen key AND every held-out key, and count an option only if it hits the target with 0 wrong on all of them. A second held-out key catches overfitting the first one misses.
- No ceiling proxies: a with-vs-without test that both arms ace measures nothing. Ask questions whose answers only the feature exposes (not derivable from names, paths, code or comments), give both arms the same data otherwise, and also record tool calls and time per arm, so a tie on correctness can still show the gain.
- Labels for line-anchored metrics: write the key's labeling rule (what "governs" means, how codebase-wide conventions count) before reading any PR, and keep conventions as a separate tag in the key; anchors can't express conventions, so the rule alone decides recall, and the bench should print both the all-pairs and the located-only number.
- Unattended runs: a test-write approval gate can block `write_file`/`patch` on test files with nobody to approve (CI files under `.github/workflows/` too). Tell builders to create the red tests with a terminal heredoc and note it in `2 insights.md`; otherwise they stage tests outside `test/` and the red commit carries no runnable tests.
- A bench that copies the repo's LIVE data (records, configs) must plant ids and names no real entry will take (e.g. 9xxx), and a later task adding real entries reruns the earlier benches: a planted `0016` broke once a real record 0016 landed.
- Shared registries (MCP tool lists, CLI usage lines, workspace deps): assert presence (`toContain`), never the exact set. Parallel tasks each add an entry, and an exact-set red test then fails at integration and needs a ruling. The reverse also bites: a registry test added on one branch ("usage lists every dispatched command") fails once another branch's new command merges, so run the full check after every merge batch, not only per branch, and fix the registry entry on main in its own commit.
- Log the TRUE exit of every run, flaky ones included; a rerun is a new line.
- Frozen scored runs execute product code from a pinned copy (a worktree or archive at the frozen sha), never the live main checkout. Merges during a multi-hour run otherwise change frozen files under it. If one already happened:
    - re-hash the `FROZEN.sha256` list;
    - diff each changed file and say whether the executed path changed;
    - record the deviation in the freeze file, keep or void the runs on that basis, and don't rebuild main's dist until the runs end.
- Long model-call runs: cache every call on disk by a stable key (stage + case + content hash; seeds from sha256, never `hash()`), make runners skip rows already in their output, and launch them under `screen -dmS <name> bash -c '…'`. An app restart kills subagents and their background processes; with the cache and skip-done, a resume costs only the missing calls. Subagents can't receive their own process-completion notices, so they must poll a log.

## 5. Builder chats

- Brief at the top of `tasks/HANDOFF.md`: the startup files to read, the goals file, each task's contract path, the loop steps with exact ledger commands (claim with `--git-worktree`, hand in, review, integrate), the never-list, "the user may not be watching", and a final answer of a few lines (each task's state and metric vs target, the report path). Launch per spawn-agent's Hermes recipe.
- Parallel chats on one repo: each brief names its own tasks and forbids the others'; shared report files are append-only; on a git `index.lock` error, wait ~10 s and retry. Kill processes by pid only, recording each one you start: parallel chats on one machine run look-alike processes (test daemons, dev servers), and a pattern kill (`pkill -f`) takes down another chat's.
- Subagent goals and contexts carry concrete absolute paths only. A leftover `<placeholder>` (even `<cmd>` or `<=`) makes the dispatcher reject the whole batch, so fill every slot before sending. For long briefs, write each to a file (`scratch/<project>-build/briefs/<id>.md`) and keep the goal to one line pointing at it: shorter dispatch, re-usable on re-dispatch, and nothing for the placeholder check to trip on.
- A user correction while children run: `delegate_task(action='steer')` each affected child the same turn with the correction verbatim plus the docs it must now read, then record it in takeaways. Don't wait for them to finish and redo.
- A child that dies mid-work (disk full, app restart) leaves uncommitted edits in its worktree: free the cause first (`df -h`), then re-dispatch with the partial files listed, its transcript tail path, any steers it got, and "verify each file before keeping it".
- Gate load-sensitive full checks on the 1-minute load: `sysctl -n vm.loadavg` prints `{ 1m 5m 15m }`, so the value is awk `$2`, not `$1` (`$1` is `{` → 0, and the gate never waits). The 5-min average lags too much to gate on.
- A check that fails twice on "timeouts" is not load until reproduced: run the same full check yourself in the failing worktree before any retry. vitest's `Timeout calling "onTaskUpdate"` with every test green means one test file blocked its worker for >60 s with a synchronous child (`execFileSync` build/pack/install in `beforeAll`, an n-iteration latency loop); rerunning that file alone hides it. Fix the test (promisified `execFile`, smaller default n behind an env var for the full measurement), not the gate.
- A step that times out at a different tool or case on each run, on main too, is usually non-hermetic input, not load: check whether the code under test reads the machine's own state (agent session logs under `~/.claude`, `~/.codex`, `~/.hermes` via `homedir()`, global configs). Spawn it with `HOME` (and `USERPROFILE`) set to an empty temp dir so the test checks the package, not this machine's history; prove it with two consecutive green runs.
- Disk before every heavy step: check `df -h /System/Volumes/Data` before a Docker image build, a clone or a new worktree (keep ≥ 8 GB free), and put a disk budget in every child brief ("keep scratch under 500 MB, delete what you create, no image builds unless free ≥ 8 GB"). A full disk kills every running child at once (Hermes can't save the turn) and can leave Docker's containerd with I/O errors; free space with merged-clean `git worktree remove`, npm cache, your own scratch and old test temp dirs in `$TMPDIR` (pack/install/export test runs leave ~70 MB each: `find "$TMPDIR" -maxdepth 1 -name '<project>-*' -mmin +60`), never the user's Docker images.
- Children share the coordinator's terminal state and the repo's git config: any `export` a child runs (HOME, PATH, DATABASE_URL, a plugin-root var) persists into the main shell and into screens launched from it (a full check then ran against a dropped test database), and a child's bare `git config user.email …` in a worktree writes the main repo's `.git/config`, because linked worktrees share it. Every brief says: env per command (`HOME=/tmp/x cmd`) or in a subshell, never `export`; git identity only as `git -C <own temp repo>` or `git -c user.name=…`. Before each commit/merge batch and before launching a long check: `echo $HOME`, `env | grep -E 'DATABASE_URL|scratch'`, `git config --show-origin user.name`, `git log -1 --format=%an`. Amend an unpushed wrong-author commit with `--reset-author`; for already-merged ones add a `.mailmap` line rather than rewriting history.
- New approved targets mid-run go to a new chat with its own tasks: a running chat takes no new instructions until its turn ends.
- Within minutes of launch, confirm the chat's first `ledger move … running` commit: proof it read the brief and claimed work.
- Find each new chat's session id before registering it. Record `date +%s` before launching, then about a minute later select sessions with `cwd` = the repo and `started_at` ≥ that time, and match each one's first user message to its prompt's opening words. Chats launched together start seconds apart, so the start time alone can't tell them apart. Launch them a few seconds apart, one screen each.
- The coordinator itself stalls silently when its turn ends or is interrupted mid-loop, and the user sees nothing moving. At every task transition (claimed, submitted, verified, integrated), not only at checkpoints, append one dated line to `tasks/loop-report.md` saying what is running now and what is next. A stall is then visible in the file, and resuming takes one line.
- Resuming a stalled task: check its worktree for uncommitted half-done edits (`git status`, `git diff --stat`) and give them to a fresh builder with "read the diff, keep what is sound, finish the rest", the contract and the loop rules; don't discard them or restart the task.
- The user away for hours ("just keep running until all tasks done"):
    1. Read a general "keep going" as answering the launch and retry decisions. Product choices stay OPEN, so record it as a build go on those decisions, not as acceptance. When the user later says to settle them "as instructed before", find the earlier instruction each one follows and record THAT as the answer, quoted, with its source. Use the recommendation only where no instruction exists. A recommendation that narrows or delays what he asked for earlier ("server only after a pilot" against "full enterprise-grade") loses to his ask, because recording it as his decision turns your hedge into his scope, and he will later be told his own request is "by design" out. Paid runs, accounts and people studies stay out.
       A blanket approval ("do whatever's recommended, I approve") IS acceptance, unlike "keep going":
        - record it once as its own decision via the atomic id allocator, quoting the user;
        - triage every OPEN row into DONE (cite task + commit) · SUPERSEDED (name the later decision) · APPROVED-TO-BUILD (scope, size, dependencies, ranked queue) · NEEDS-PEOPLE (draft the interview guide, recruit message and pilot sheet now) · REC-NO/LATER (stays as recorded);
        - set statuses with a note naming the blanket decision, never changing ids;
        - a paid-spend recommendation with no key available is met on the subscription path where one exists. Say so instead of buying anything.
       Then dispatch the new asks in the same message as parallel tasks (research and build), with ledger tasks only for code.
       When the queue empties and the user said to keep building, start the next wave yourself the same turn: pick from established goals and sources already written (ranked lists in research outputs, open backlog items, reviewers' deferred findings, the next measurement the last result calls for, evidence aimed at the user's audience such as backend-engineering reliability numbers), write one shared brief file with a section per task, record the pick and why in takeaways + insights, and dispatch. Don't wait for approval of tasks that follow accepted goals.
    2. Make every buildable task `ready` (section 3), split them into streams by dependency (one builder chat per stream, parallel tasks inside it), and put each builder's prompt in full in `tasks/HANDOFF.md`. The scratch prompt file is only a launch copy.
    3. Register every chat before launch, then launch. Check free disk first (`df -h`): each builder worktree with node_modules takes ~200-400 MB. If space is tight, `git worktree remove` (no `--force`) every worktree whose branch is merged into main and whose `git status --porcelain` is empty. Merged branches keep their commits, and a dirty or unmerged worktree is kept automatically.
    4. Add a no-model cron watchdog (`no_agent`, every 15 min, a repeat count so it ends). Each tick it:
        - rebuilds the board;
        - resumes a builder that gave its final answer while its queue still has open tasks, at most 2 times. Compare the final answer's time with the last resume, or a resume that hasn't started yet looks finished.
        - warns once on a chat quiet 45 min;
        - starts one wrap-up chat when all have finished or a deadline passes.
       Keep its state in a plan file (sessions, queues, resumes left, the wrap-up with its own `id`, prompt and report path). Agents launched mid-run go into the same plan file and push the deadline out, so the wrap-up waits for them too. A later run reuses the same script: archive the old plan (`plan-<time>.json`), write a new one, and raise the existing cron job's `repeat` instead of creating a second job, since two ticks on one plan can double-resume a chat. Before relying on it, test every case on a temp plan with the launch call stubbed. Example: `~/.hermes/scripts/mole-overnight-watch.py`.
    5. The wrap-up chat has its own brief. It checks what really changed before folding results into the pages: git log on main, each task's last `runs.jsonl` line vs target, and a fresh full check. The builders' answers are claims. Then it writes one report the user opens first.
    6. "Build everything, fully working, connected into the final product": each builder brief names the surface every feature lands on (view section, file tree, plugin hook, MCP tool, server endpoint), and the wrap-up brief makes a reachability table (feature → surface → how checked on the repo's own data), wires gaps with one import + one call plus a reachability test, and never changes feature logic or keys.
    7. Merged isn't shipped: the wrap-up also packages every user-facing surface (editor extension, agent plugin), runs its install check, and installs it where the user works. The repo's check command type-checks and tests but never bundles, so a new runtime dependency can break the package while every test stays green, and the user keeps running an old build.
       Public exports: the private-string redaction may touch comments only (a real parser per language: the TypeScript parser, Python `tokenize`; never a whole-file regex, which rewrote a default path inside code). A forbidden string left in code fails the export so the source gets fixed (user-facing runtime strings count: an error message citing a private task path is a leak, so point it at a public doc), and a test asserts exported code minus comments equals the source. Run the export scan on main before closing each merge (with the targeted tests), not only before a push: newly merged proof scripts and tests carry private task paths and names that fail it later, far from their cause. Run the secret scan and the push as one `scan && push` command, never scan after.
- Monitor with `python3 -B tasks/loop_status.py` and Hermes `state.db` (`sessions.message_count`, `last_activity_description`). An exited screen only means the CLI client returned; the session can still be working.
- One main file per builder chat, plus a board of active and upcoming chats. Hand-keep only a registry (chat id, ledger owner name, job, queue, what it needs from the user). Generate the rest from `state.db` and the ledger:
    - main info + handoff (state, usage, the start of its final answer, the resume command). Hermes' `estimated_cost_usd` is an API-price estimate; on a subscription nothing is billed per token, so label it "≈$X API-price" and never report it as money spent;
    - a progress timeline from each task's `4 log/ledger.md`;
    - results from the status script, further work, needs-you, helper subagents, the user's messages to that chat.
    - Keep a `Handoff notes` section the agent writes and the generator never touches.
    - Fail generation when a running, submitted, verified or blocked task names an owner missing from the registry.
    - Flag a task still `running` whose chat has gone quiet with no final answer.
    - Register every worker chat that ran on the project, finished ones and non-ledger ones (a tool trial) included. An agent without ledger tasks keeps its own step log (`YYYY-MM-DD HH:MM  step  detail` lines) and a `results.jsonl`, and the generator reads both. Otherwise the board can't show it at all.
    - Board tables: split working + upcoming from finished, so each stays within the row limit as chats pile up. Show the ledger state of queued tasks the agent hasn't claimed yet; otherwise a fresh builder's row reads 'none'.
    - On relaunch or a changed plan, replace the stale brief in that agent's handoff notes with a pointer to the new one. A brief that still says to take over finished work misleads the next reader.
    - Rebuild the board and read `git log` right before proposing a takeover: a chat stalled by sleep or power loss can resume and finish the task itself, which turns the takeover into a different decision.

## 6. Checkpoints and result pages

- Dogfood checkpoint ("run it on the repo's own last N changes"): use the benchmark's own change set for that repo, so the truth is already known. Save the raw per-change output beside the report (`tasks/c4-dogfood.json`), and report the hits, the false hits, speed, and what it got wrong in a reader's eyes (wrong "why", extra fixes from a too-broad rule), not just the counts.
- Adding a decision, changing a decision's status (OPEN → the user's), or a builder logging a new metric value breaks every page renderer that counts decisions, quotes his answers or pins a number. Rerun ALL core page renderers in the same turn (not only the page you edited) and fix the stale pages, or name the failing ones in the wrap-up brief. A new OPEN decision must also be placed in a hub theme, swapping out a settled one to keep the theme within its row limit. The failure is the page going stale, not a check to loosen.
- The same turn also updates the page the user reads first (his dense ideas/core file or hub): its "state/next" lines for every task that got built or started. Results that land only in deep pages and task logs read to him as "not reflected". If his own source notes file grew, re-pin the copy the pages quote, place his new lines, and fix the line refs that shifted before rendering.
- "Is it all done / how do I see and test it?": answer with a try-it file in the plan folder (notes style), not a status table. Build it from fresh evidence this turn:
    1. full check + `loop_status.py` + the wrap-up report for what's merged, blocked and never started;
    2. compare each surface's INSTALLED version (`code --list-extensions --show-versions`, plugin list) with main; rebuild, install-check and install any that lag;
    3. run every command you list once (CLI on the repo itself, MCP over stdio, hook scripts with a piped event) and write only what ran;
    4. sections: state · one place (artifact paths + install/load command per surface) · try per surface, in the product first (the editor view, hover, file tree, Problems, the agent plugin), the CLI last as "also scriptable" · not done (blocked with numbers, not built, needs the user) · recommended next.
    A feature reachable only from a terminal counts as not done for the user: list it under not done with the missing surface. Never call something the user asked for "not built by design"; check his own instructions first, and if a phase gate came from your recommendation, say it's a gap. Link the file from the hub.
- "What was built in these runs / is it all documented?": answer from a build-summary page in the plan folder (Summary on top, then notes rows grouped by goal: task · what it does for the user · merge sha · date · where it's documented), built from `git log --merges` since the run began, not from memory. Audit while writing it and fix the gaps the same turn: every merged task has a task folder (builders working only in fixtures or docs sometimes leave none), each task's `0 start.md` status says MERGED with the sha (builders leave "built, not reviewed"), every user-facing surface is in its README/docs, and the hub's "what's built" section points at the page. List what stays open (missing prior-art notes, stale ledger states, not yet public) instead of implying full coverage. Prevent the drift by doing the status line + docs check as part of each merge.
- Before a builder's benchmark number goes on a resume, a fresh reviewer recomputes it from the raw per-case rows with its own script (answer-key hash checked), walks the builder transcript for held-out runs before the final one or tuning after it, greps the code for hardcoded case ids, confirms cost uses the same model/price table with every call counted, adds Wilson 95% per split and a paired McNemar exact test vs each baseline, and returns one resume-safe sentence. Say "beats" only when the paired test is significant; otherwise word it as the measured change with n and interval ("raised recall from 52% to 96%, n=61, 95% CI 79-99%, at under half the cost, with fewer false alarms"). A clear held-out gain that missed its own dev gate can still merge: record the missed gates as a deviation in `--findings` and narrow the claim (R7), never re-tune on held-out.
- Significance cuts both ways: with a non-significant paired test, write neither "beats" nor "lost". Say "no measurable gain" with the numbers and p. A first small batch (1 run per cell) that reads as a loss can level out over the pre-registered epochs, so report per-epoch beside the total. Score infrastructure failures (gateway drop, agent crash) as 0 and keep them in (intention to treat), and add the excluding-them figure on one line. When the full run lands, replace the partial-batch numbers on every public page (README, site, release notes) in the same turn: grep for the old digits.
- Before a number from an integrated task goes on a resume or pitch, read that task's last few `runs.jsonl` lines and notes, not just the status line. A builder that missed may have edited the key builder or changed the bench's exit gate so the run passes (an R2/R7 breach even if the real number is still printed): mark it "don't cite until checked" in the claims file and say so to the user.
- Benches and tests that need a database often skip silently without their env var (`it.runIf(process.env.X_DATABASE_URL)`), so a green check can mean 0 database tests ran. To verify "is the Postgres part done": grep the tests for `process.env`, create a throwaway db (`createdb -h /tmp <name>`), export every URL var they read, run those packages to 0 skipped plus the bench, then `dropdb`. Re-measured speedups vary with host load: cite a range or the lower value.
- Bench the process you ship, not its library: start the real entry point (server binary, extension host, hook script) on real inputs once per checkpoint. A queue bench passed while the shipped server enqueued jobs and never registered a worker; unit benches can't see missing wiring.
- "Is the core code as good as it gets?" (before more benchmarking): first say which plan items are built vs only planned (grep packages + ledger; a W1-W12 list is a work plan). Then run one read-only auditor per area in parallel (storage/time, capture/schema, checker, agent surfaces). Each shallow-clones the mature open-source projects for that area, pins repo@commit, reads their code and tests (not READMEs), and writes rows: component · our path:line · their path:line · what they do better · borrow / replace / keep · licence · effort, as .md + .json in `systems/core-audit/`. Rank by user benefit, turn the top rows into ledger tasks, and queue tasks that touch in-flight tasks' files until those merge. Check every "not built" claim an auditor makes against main before relaying it, since auditors can read stale trees. Ask auditors to look for engines already in our repo but never called (an unwired dependency-cruiser rules engine beat any new borrow), and when we keep our own parser, keep the official one as a dev-dependency test oracle diffed on 15+ inputs including invalid ones it rejects.
- "Justify all the design decisions / be critical": a verdict table first (decision · keep / reframe / fix / cut · one-line reason), then per decision the evidence path, why it's right, the honest limit, and what to say instead. Check each against the code (grep imports, schemas, workflows), not the plan pages: plan prose said "two linked graphs" while the server never imported the temporal package. Proposed fixes become OPEN decisions on the hub; nothing is applied until the user picks.
- At each checkpoint the builder writes `tasks/loop-report.md` (every metric's latest value vs target, what missed, what's next) and runs the status script.
- Pages that state results (a plan, a resume) read `runs.jsonl` and ledger states at render time and count what's true today; a target turns true only when its task is integrated and its metric logged. Never hand-copy a metric. Prose that has to quote a measured number keeps a phrase → pattern table in its renderer, matched against `loop_status.py` output at render time, so a drifted number fails the render.

See also: `fix-loop-metric-gate` and its worked example (`references/worked-example-path-links.md`) -- what a slow 21-round fix looked like, and the preflight that makes it first-try.
