# Build vs buy for a custom pipeline

Trigger: "why aren't we using <bookmark app / fetch layer>", "how about <tool>" about a pipeline the user already runs. Narrower sibling of `tool-gap-analysis` (use that for harness/app comparisons and shared threads). Output: what we have, whether a decision was ever recorded, a ranked list of pieces to build in. Not an adopt/reject verdict per app.

## Steps

1. **Task folder first** (`docs-over-chat` §0), even if the chat began as a quick question: create it, move notes already written into it, map the chat id (find it with `sqlite3 ~/.hermes/state.db "select distinct session_id from messages where content like '%<phrase>%'"`; the newest session is often another chat, or this chat's own delegate_task children: rows with `source` = subagent), and re-dump `hermes session folders.json` with `indent=2` so the diff stays small.
2. **Baseline the incumbent from its data.** Query the live store read-only for decisive counts (rows per source, rows missing the field a tool would fill, private-flagged count, usage rows of every review/triage step: 0 means have, unused) and grep the code for the feature (`fts5`, the archive platform list). Many gaps are a feature that exists for one source only. Save as `systems/our-system.json`.
   - Read the live config by section headers and named keys with secret-looking lines dropped (`grep -nE '^\[|^name|^path|^enabled|^backends' <config.toml> | grep -viE 'key|token|secret|pass'`): pipeline configs hold API keys, and a baseline must never print one.
   - The incumbent includes the user's manual habit: read their own notes read-only (never edit) for the units, buckets and capture format they already use (a running label-line + link input file, their own word for an extract or a holding bucket) and log each with path:line in `1 takeaways.md`, so a design for a new stage is built from their words instead of a new vocabulary.
3. **Check for a recorded decision** by grepping project, context and notes folders for the tool names (exclude saved-bookmark data and vendored site-packages). Nothing found → say "no recorded decision"; never invent a rationale.
4. **A pasted AI overview is unverified.** `gh api repos/<o>/<r> --jq '[.stargazers_count,.pushed_at[:10],.license.spdx_id,.archived]'` (stars, licence, last push) + README for each tool; a name you cannot locate, or a repo that 404s (moved to another host), is UNVERIFIED, not described. Evidence for scale/RAM/import claims: `gh api repos/<r>/issues/<n>/comments`, the tool's OpenAPI spec (what its create endpoint accepts), and forum threads; if `web_extract` errors with a search-only backend, fetch with `curl -sL -A <browser UA>` and strip tags (reddit `.json` is bot-blocked: cite the search snippet and say the thread was not opened).
4b. **Sweep every layer of the problem, not just the bookmark apps.** A saved-items pipeline touches: fetch/crawl/extract (trafilatura, defuddle, Crawl4AI, ArchiveBox, SingleFile, yt-dlp/gallery-dl) · bookmark/read-later apps (Karakeep, Linkwarden, Wallabag, Linkding) · connectors/ingest plumbing (dlt, Airbyte, Onyx, RSSHub) · note apps + capture→route funnels (Obsidian Web Clipper, Memos, Open Notebook) · personal-data unifiers (Datasette/Dogsheep, HPI). Give each layer its own table with stars, last push, how it works, evidence and a verdict (use · pair · borrow · skip · unverified), repos first; consumer apps (Raindrop, Readwise Reader) appear only as a named reference bar, flagged as not researched. A table of 5-6 bookmark apps reads to him as missing research; check 60+ repos' live stars/pushes with `gh api`, read READMEs for the shortlist, and say which tools were not run on his data.
5. **Classify each tool, and our own system, by the stage it covers:** in (collect · fetch/read · store/archive) → make sense (extract the passage unit · classify/tag · route) → check (confirm/correct · learn from corrections) → use (reader UI · search · resurface · export). An agent fetch layer is not a store; a bookmark app is not a multi-source collector; routing whole links into config targets is not routing passages into the user's own note files, so say which one exists.
6. **Default stance (user): take the best, build it into our system** by cost-effectiveness and concision. Prefer libraries already in the venv (trafilatura, yt-dlp, sqlite FTS5) over a new service; list what to skip with the reason (extra server, AGPL dependency, login-cookie exposure, URLs sent to a third party). Write `systems/takes.json`: rank · take · from · have (verified) · cost · value · verified.
7. **Keep it reversible:** data stays in the user's DB (columns via `ALTER TABLE` migration on open) plus one export (Netscape bookmarks HTML + JSONL) so any bookmark app can import later. A third-party fetcher sits behind the existing privacy screen.
8. **On "go": one ledger task per take** (`ledger` skill). Independent takes run in parallel worktrees; a take that needs another's code stays `proposed` until that one is integrated.

## "One place to see/search every source" (unified view)

- First report what exists and whether it is one place: list each reader page, dashboard and search command with what store it actually reads (a dashboard on the legacy DB and a CLI search on the same DB do not cover post files kept as jsonl). "Separate pieces" is the honest answer when they are.
- Default candidate: Datasette over ONE unified SQLite (our own `items` table: source, ext_id, author, title, body, url, created, private flag; FTS5 with porter; one importer per source, dedupe by id) = the Dogsheep pattern. It gives search box, facets, JSON API and localhost serving with no UI code; a nicer thread/article reader is a small template that links to the long-read page. Bookmark apps (Karakeep, Linkwarden) re-crawl every URL: for tens of thousands of already-stored posts that duplicates work and is slow/RAM-heavy, so pair them at most for outside-link pages. Static search (Pagefind) hits memory limits around 50k pages.
- Prove it with a scratch spike before recommending: build the db from the real files in `~/.hermes/cache/scratch`, skip `over_18`/private rows and print only counts, time a few FTS queries, run `datasette <db> --get "/<db>/items.json?_search=<q>"`. State what the spike did not cover (e.g. article bodies not indexed).
- Raw store files repeat rows (several epochs per post): count unique ids before quoting a size, and make the importer dedupe.
- Ask the choice once, as one decision with the recommended option first. If he answers with "just build it, whatever is best" (or has already said "build the best of what exists"), that is the go: build the evidence-backed pick without re-asking, and leave only genuinely separate sub-choices (e.g. how to fetch outside links) open.
- Build recipe, launchd serving pitfalls, the acceptance script, and the app layer (plugin API + single-page UI, outside-link crawl, local meaning search): `private-library-pipeline/references/local-search-view.md`. When he then asks for "a full backend + frontend, like an app, run for hours", extend the same Datasette process into the app rather than starting a second stack, and start the long jobs (link resolve/crawl, embeddings) detached first so they run while the UI is built. Privacy screen the served db at build time (adult rows to an unserved db) and test it with a content search: the source's own adult flag misses posts.

## Before proposing a passage/route feature

- Run a 1-item local pilot of the riskiest stage (ollama only, public article) and put its numbers in the design, labeled demo-not-eval. For any LLM choose-from-a-list step, rerun with the list reversed: answers that flip with order are position bias, not a decision (T6 test: 3/3 top-1 routes flipped, stated confidence 0.7-1.0). A second router (embeddings) that must agree is the cheap gate.
- Links the user already placed by hand in their own notes files are free ground truth for a routing replay eval (url → file); count them before asking for labels. A second, larger replay: hide one of his own note chunks and ask the router which file it came from (leave-one-out). Report both numbers; the hand-placed-link one is the honest one.
- When he then says "get it done, run for hours" for the passage → notes funnel: close the open design decisions with their recommended options, write each as a decision row marked as applied on his go (reviewable), say which one changed because of what he asked (e.g. bulk saves now go through the funnel), then build per `private-library-pipeline/references/extract-route-funnel.md` (grounded picking, local models, router measured, review view + one generated file, never editing his notes). Start the long model pass detached first, build the UI while it runs, and have a loop re-route and rewrite the output file every ~20 min.
- `trafilatura.fetch_url` returns None when a site 404s its bot user agent (bearblog): retry with a browser user agent before calling a page empty.

## Fan-out pitfalls (ledger tasks with child workers)

- A code repo that is its own git repo needs only `git worktree add -b <branch> <dir> main` + `ln -s <main>/.venv <dir>/.venv`, then `ledger move <task> running --worktree <dir> --branch <branch>`.
- An editable install resolves the package to the MAIN checkout: have workers run `PYTHONPATH=. .venv/bin/python -m pytest -q` and print `<pkg>.__file__` first, or the suite silently tests main.
- Worker brief: exact boundary files, no ledger moves / merge / push, commit on branch only, proof on a `VACUUM INTO` copy of the live DB (never write the live one), counts only for private content.
- Rerun each worker's tests yourself before `ledger move submitted`; that move reruns the suite and can exceed a 180 s tool timeout, so run it with `timeout=600` and confirm via `ledger board`. Put only numbers from a run you did in `--checks-result`, never an expected count.
- Merge order: `git merge --no-ff` each branch into main, rerun the whole suite on main, then `ledger move integrated --merge <sha>`; a dependent take (needs another's hook) starts only after that merge, from the new main.
- Merged ≠ switched on: leave the live config untouched, name the one key that enables it, and ask before any bulk network run over the user's saved items.
- Before enabling any ingest/archive over the existing DB, count items per `sightings.source/kind` (not just `platform`): the table also holds old imports, open tabs, pins and likes. The user wants only real bookmarks to come in; if the platform column is the enable switch, it pulls all of those. Turn the job off and ask which source is the user's bookmarks rather than guessing. A batch already run over the wrong sources is reported, not silently deleted.
- A new saved-items source ("same job as the X bookmarks, for Reddit") is its own ledger task modelled on the existing reader, not a config flag: see `references/bookmark-source-jobs.md`.
- A reviewer P1 is fixed in the worktree with one regression test per finding plus the full suite, then recorded as `verified --findings "P1 … FIXED; P2 accepted"`; a second review is not needed when each fix has a test that fails without it.
- Tasks that all edit a shared entry file (CLI module) conflict at merge: decide the merge order up front (three tasks touching the CLI module merged cleanly in sequence with `--no-ff` when each added a separate subcommand).
- A child's own proof command can fail on its environment (macOS has no `timeout`), and the harness may block a review probe that contains SQL such as `DROP TABLE`: the worker then reports a probe it never ran. Read the child's report for "not executed" lines and say which attacks were reading-only.
- When the user corrects scope mid-run ("just X and reddit", then "just the bookmarks"), change the live config via a backed-up copy (`config.toml.before-<change>`), record the correction as a USER decision that supersedes the earlier one in `systems/decisions.jsonl`, and add the verbatim line to the task `1 takeaways.md` plus the global takeaways inbox.
- Reviewers are fresh contexts, not the worker: P0/P1 only, an executed reproducer per finding, no private text in reports.
- Ingest-feature P1s reviewers actually found, so put them in the review brief: (1) a network step for privacy-gated items must run only after the stage that can still mark an item private (classification rules, hidden leaves), else it fetches and then files a public copy; spy on `subprocess.run`/`net.fetch` across the full stage order, not one function. (2) An external CLI (yt-dlp) fed a stored URL must be limited to the single-item URL shape; channel/playlist URLs make it walk many items and file the wrong one. (3) FTS5 external-content indexes desync on `INSERT OR REPLACE` (the delete trigger does not fire): keep a `--rebuild-index` command.
