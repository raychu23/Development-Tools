# Adding a saved-items (bookmarks) source job

Use when the user asks for the running X-bookmarks background job to be repeated for another platform. The shape to copy is the existing reader (resumable store + state file, throttled paging, fail-closed fixed error messages, aggregate counts on stdout, one HTML notebook, a loop driver script with caffeinate/disk guard). Reuse its helpers by import; do not edit them.

## Order

1. **Prove auth by hand before writing the brief.** Read the logged-in browser profile's cookies in memory (gallery-dl's cookie loader with the Arc keyring shim used by the X job) and print only names/lengths/status codes. Try the cheap routes in order: cookie request, then bearer/session token from the cookie jar against the platform's API host. Record which one returned 200 and which got a bot wall (403); the brief names only the working route and forbids the other.
2. **Probe the listing, counts only:** page size, cursor field, rate-limit headers, kinds returned (posts vs comments). Platform listing caps (Reddit lists at most ~1000 saved items) mean the end of the list is `capped`, not `complete`; older items need the platform's data export. Say this to the user up front.
3. **Ledger task + sparse worktree + one worker**, brief = the verified facts, behaviours (account check every run, dedupe by stable id, per-invocation page bound, cooldown on 429, `--refresh` that stops at the first known page, hostile text escaped, no external requests when the notebook opens), exact boundary files, a scratch-dir proof run limited to 2 pages, and "counts only, never titles/text/tokens" (saved lists contain adult content).
4. **Review → merge → start the driver** only after the merge; the driver script lives in the task folder and logs aggregate JSON lines to a run.log beside the private store. Report where the notebook and the log are.
   - Start it detached: `screen -dmS <name> caffeinate -i python3 run_loop.py` (from the script's folder), confirm with `screen -ls`, then read `run.log` after the first invocation (it is written at the END of an invocation, so a missing log in the first minutes is normal; `posts.jsonl` growing shows progress). Tell the user the stop command (`screen -S <name> -X quit`).
   - Live proof commands in worker briefs must not use `timeout` (not on macOS); the bounded `--max-pages 2` flag is the bound.

## Reddit specifics (verified live)

- Auth drifts, so re-probe before each build: the bearer `token_v2` from the Arc profile cookie jar against `oauth.reddit.com` (`/api/v1/me`, `/user/<name>/saved?limit=100&after=`) worked at first, later every python `requests` call (bearer, cookies, even anonymous curl) got a 403 bot-wall HTML page from the same machine. Reddit fingerprints the TLS client: `curl_cffi` with `impersonate="chrome"` plus the profile's cookies (in memory) returned 200 on `old.reddit.com` and `www.reddit.com`. Install it into the shared venv and list it in `pyproject.toml`; never print cookie values.
- Several browser profiles may hold different accounts (here: Default = a second account with 5 saves, Profile 2 = the real one). Identify each by `old.reddit.com/api/me.json` name, then use only the account the user named.
- Comments endpoints (`/comments/<id>`, `/api/info`, `/search`, `/api/morechildren`) returned 403 for the bearer token; retest through the cookie + impersonation route before telling the user comments are impossible. Collectors that give up mark items `skipped`/`unavailable`, so a retrofit pass must retry those once.
- Rate limit for the bearer route is 100 requests per 10 minutes and blocked 403s count; paging is 1 request per 100 items, images and comment attempts hit the cooldowns.
- **Every listing route can under-count.** The oauth listing, `old.reddit.com/user/<n>/saved.json` and the old HTML page all stopped at the same 399 while the new-reddit web feed (`GET /user/<n>/saved/`, then the `faceplate-partial` URL `/svc/shreddit/profiles/profile_saved-more-posts/new/?after=…`, ~25 `<shreddit-post id="t3_…">` per page, 1.2 s apart) listed 580. When the user says there are more, believe them: walk every route with ids only, report the overlap table, and union the missing ids via `old.reddit.com/api/info.json?raw_json=1&id=t3_a,t1_b…` (100 per call, serves comments too; `by_id/…json` silently returns only 25 per call and no t1). A short listing is `complete` only for that route; the notebook status should say which sources ended.
- **A 0-post page in the web feed is not the end:** the feed lists posts, then the saved COMMENTS (`<shreddit-profile-comment comment-id="t1_…">`) behind the same partial chain; stopping at the first 0-post page left ~500 saved comments (and the user's "far more" complaint) unexplained. Walk until a page with items has no next link, and re-request that cursor to confirm. The listing APIs hide ~half the saved comments too.
- A data-export link left open in the user's browser tab is a signed S3 URL that expires (curl returns AccessDenied): do not rely on it, and ask for a fresh request only if the live routes fail. AppleScript `execute javascript` against an Arc tab timed out; the browser tool refuses a real profile unless the default browser is Chromium. Prefer the cookie + impersonation route.

## Reviewer P1s found in this kind of collector (put in the review brief)

- Text from the platform can contain a lone UTF-16 surrogate (truncated emoji): it is valid JSON, passes the store, then fails the utf-8 HTML write on every run and a driver that exits on `error` never produces the notebook. Sanitise strings at extraction and write the HTML with `errors="replace"`.
- An empty last page with a null cursor mid-listing is a provider glitch as often as a real end: halt once with a short cooldown and accept `complete` only on a second look (see `external-data-integrations` §5 for the verified-end rule).
- Web-feed walker, three ways to say `complete` wrongly: (1) a 200 login/consent page or a page whose markup was renamed has no items and no next link (or has next links but no items) → an end page must carry items, and the empty-with-next stall counter must live in the persisted state, not a local, or one-page-per-invocation runs reset it; (2) a chain cut short at a page that lost its next link → require the walk's id count to be ≥ the other route's count before completing; (3) the next link regex run over the whole page matches a path inside a post title → read it only from the `faceplate-partial` element's `src`.
- Per-post follow-up fetches (comments): a burst of 403s is a block, not a verdict on those posts. Mark an item final only on 404/410, or when the endpoint works again later in the same invocation; otherwise leave it retriable, or the next pass reports `complete` over permanently empty comments.
- Do not record a count as accepted because the user said "yes" to "does 399 look right?" in passing: store it as provisional until the notebook is opened; the later "there are far more" supersedes it.

## Keep apart

The reader writes its own private store and notebook. It does not write the main item DB and does not reuse legacy rows: the DB's older imports were not bookmarks-only.
