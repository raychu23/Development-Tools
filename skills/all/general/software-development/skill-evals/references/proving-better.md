# Proving "ours is better": picking and running the tests that matter

Use when the user asks whether the product is measurably better, whether it's "already been done", what metric counts as good, which tests to run, or what would impress recruiters / interviewers. Run this before repeating any headline number or launching any test.

## Steps

1. **Read what changed first.** List files newer than the plan's handoff and other live chats on the same project; a parallel chat may already have reframed the question (e.g. "beat just asking the agent") or designed the deciding test. Build on it instead of re-planning.
2. **Audit our own answer key.** Read the key's truth definition (its `method` field) next to the system's mechanism. If the truth is the same signal the system computes (key: "changed" = code lines differ; system: flags on a body hash), the 100% / 0-false result is a definition, not a finding. Say so first, reword the claim, open a decision, and caveat every competitor row scored on that key.
3. **Score candidates on the user's criteria before picking.** When the user names criteria (e.g. frontier problem × impressive to recruiters/interviewers × matters to users), make one table: every candidate test as a row, one column per criterion, plus time cost. Pick only rows high on all of them. Sources per column, dated, recent first:
   - frontier: current papers/benchmarks on where the field is stuck (confident invented answers, context that doesn't help agents, agents' false "done")
   - recruiters/interviewers: own eval set with method shown ("the senior signal"), a metric + baseline against the simplest method, failure modes, cost + latency; vendor metric names (catch rate + false-flag rate, task success / merge rate, time-to-answer)
   - users: the product's own promises, phrased as what the user gets
4. **Baseline = what users do today, not a named rival.** Compare against the default workflow ("just ask the agent", "tests passed", "read the summary"). Never frame a test as a head-on fight with a named tool; other tools are inputs the product reads from. A test of an internal mechanism (staleness precision, scale) is plumbing: run it to fix the engine, never present it as the proof.
5. **Say each test in plain words before running it.** One line each: what it measures, which user promise it checks, what result would change the plan. If the user can't tell what a test is about, it was the wrong test or the wrong explanation.
6. **Size to the stated budget.** "A few hours" → lite versions (15-20 questions, 1-2 arms, real data already on disk) run in parallel; push paid or multi-day runs to a later decision.
7. **Design honestly.**
   - field's task + public dataset where one exists; when the system can't run on it, compute the trivial baseline from the dataset design (balanced set, "flag everything" = P 50 / R 100 / F1 66.7)
   - report the REAL mix as well as the balanced set: on real history only a small share of changes are true positives, so precision on the real mix is the number users feel
   - before running a product-vs-baseline test, confirm the product arm exercises the mechanism the claim is about; if that component isn't built yet, build it first (or name the arm for what it is, e.g. "retrieval only", and say up front the core arm is NOT RUN because unbuilt). Measuring around a missing engine produces a loss that says nothing about the engine and prompts "why isn't X running"
   - freeze key.json + sha256 before any method runs; design on a dev split, run the held-out split once
   - receipts per run (commit, dataset sha256, machine, commands, n, Wilson 95% CI); noise stated; where we lose said first
   - model: ai-memory's `docs/benchmarks/` page (public dataset, field metric names, receipts, pre-stated noise band, rerun per release, cost beside accuracy)
7b. **Does structured memory beat plain retrieval? (LLM-graded evidence-arm recipe).** For "does our records/graph help a model predict or answer X" on real public history:
   - data: real decisions with their review threads (RFC/PEP/KEP PRs via `gh api`, cache every PR as JSON) · test set = the most recent cases (least likely in training) · input = the proposal at its FIRST commit, nothing from the thread
   - labels: an LLM extracts the thread's substantive points (field practice: Liang et al. point extraction) · a 2nd, different labeler model on the same prompt → report agreement · labels never reach an answerer
   - corpus is time-respecting: only items CLOSED before the test item was CREATED, excluding itself
   - arms share answerer, prompt skeleton, output format and an equal evidence char budget: nothing extra · raw-text RAG · our records · SHUFFLED records (Liang's control: separates "relevant history helps" from "any history primes the model") · missing baselines NOT RUN
   - judge = a different model, blind to arm, predictions in random order, one-to-one "same core concern, not same topic" matching; primary metric and claim rule written in protocol.md before labels exist
   - paired bootstrap over cases for each difference; a loss is reported first with an error analysis on the lost cases; after looking, those cases are dev only: freeze a fresh held-out set before changing one thing
   - known failure: auto-drafted summary records make predictions generic and lose to raw text; keyword retrieval over records can score no better than shuffled ones → keep quotes/concrete concerns, link to the decisions a case actually touches
   - mechanics: a one-shot pure model call is `hermes -z "<prompt>" -m <model> --provider anthropic -t "" --safe-mode` (`--safe-mode` drops AGENTS/memory/hooks/MCP; pass `--provider` explicitly or it falls back to the default provider) · cache every reply as `calls/<stage>/<key>.json` so a timed-out run resumes free · seed shuffles with `hashlib`, never Python `hash()` on strings (randomized per process → cache misses and a different order each run) · run the pipeline as a background job with notify
7c. **Historical backtest of a pre-merge check ("would it have caught changes that later failed").** Field terms: SZZ (Śliwerski, Zimmermann, Zeller 2005) for the change that a later fix traces to, just-in-time defect prediction (Kamei 2013), DORA change failure rate.
   - fit-check FIRST: run the product on ~6 known-failed changes before labelling thousands. Quick finder on GitHub-merge histories: merge subjects naming a `revert-<PR>` branch → the reverted PR's merge commit, base = its first parent. If the failures are ordinary bugs the product can't see, X → Y will be X ≈ Y; say so and pick a product-related outcome instead of waiting hours.
   - labels written before any arm: failed = reverted, or SZZ-traced from a fix within N days; stuck = neither within a longer window; keep all failed + a time-stratified stuck sample, hash the corpus
   - `git log --name-only` prints EMPTY file lists for merge commits unless you pass `-m` (or diff against the first parent): every file-overlap step (SZZ, revert matching) then silently misses on merge-commit histories. Check a few known reverts are found before trusting labels.
   - report recall on failed, false alarms on stuck, both on all failures and on the product-relevant subset (two labelers, kappa); a subset label that correlates with change size is a confound — say so; check WHY each catch fired before calling it a catch
7d. **Engine/solver speed claims.** Compare on identical inputs: the field's competition instances (argumentation: ICCMA sets, grounded tasks, PAR-2 timing), a reference solver (process start counted and excluded, both reported), and the LLM-asks-for-the-answer arm on small inputs; report per-instance agreement, p50/p95 time, cost, and time after one edit vs full re-solve.
8. **Delegating test agents.** One shared brief file: time cap, write-only results folder, read-only clones in scratch, 0 model calls inside the measurement, freeze-key-first, receipts, ≤60-line notes-style report, final answer = paths + headline numbers. Verify every child's claims yourself (open the report, re-hash the key) before reporting; children misstate durations and scope.
9. **Report.** Verdict first ("not proven" when it isn't) · what each test was, in plain words · the weak spot · the next test ranked by the criteria table · decisions with a recommendation. Full doc under the plan's `systems/<topic>/` with the ask saved verbatim and sources under `research/`.
