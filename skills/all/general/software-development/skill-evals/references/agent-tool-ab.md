# A/B: does a tool help an agent on real code questions

Use when the claim is "agents are cheaper/faster/more correct with tool X" (a code map, MCP tool, index) rather than a prompt or skill text. Different from the tool-free promptfoo path in SKILL.md: the agent here must have real tools and read a real repo.

## Design
1. Conditions: A = built-in tools only; B = tool offered, agent decides; C = same as B plus one sentence "start with the tool". B alone often shows the tool is ignored (a grep wins), so C is what isolates the tool's value; report tool-use rate per condition next to every cost number.
2. Tickets: >=10, several question types (callers, importers, transitive impact, call path, definition+callees), written with answer keys BEFORE any run, keys from a different code path than the tool's own index (e.g. TypeScript language service vs the tool's checker walk), dated earlier than the first run. Hand-check 3-4 keys with grep/read.
3. Repetitions: >=2 per cell, same ticket/rep paired across conditions. Report paired differences and a sign test; reps of the same ticket are not independent samples, so say "N tickets x R reps".
4. Fixture: a scratch COPY of the repo, read-only for the agent; confirm the original's `git status` is clean before and after. Delete the copy's own agent-instruction files (AGENTS.md, CLAUDE.md) so agents do not read the repo's rules, and for a monorepo take the file list from the tsconfig, not a `src/` dir. Scratch dirs are pruned after a day idle: archive briefs, answers, tickets and the graded JSON into the project (a tgz) before closing the task.
5. Briefs: one file per run in a scratch dir; the goal handed to the agent is just "read your brief at <path>". Briefs for A/B/C must differ only in the tool paragraph and the C sentence (diff them). Put the answer path in the brief and delete old answer files before reruns: a stale file makes write_file refuse and the agent reports success on someone else's answer.
6. Dispatch: parallel batches of 10 background subagents, at most 50 subagents per assistant turn (the runtime blocks the rest as a runaway loop: say plainly which runs were NOT started and re-dispatch them next turn; never describe blocked runs as running). Make the harness take env parameters (run-id prefix, fixture path, ticket file) so a second repo reuses it unchanged. Each run's session title carries a run id (`m15 B-T07-r2`) so a grader can join accounting by title. Take tokens, cost, API calls, tool calls, wall time from the harness's own session table, not from the agent's self-report. Detect tool use from recorded tool calls (regex on the command), and verify against 3 transcripts.
6b. The tool arm gets the product's REAL output, captured verbatim (run the hook with a synthetic tool-event JSON, or call the MCP tool over stdio) with the command saved beside it. A note the experimenter writes by hand leaks what the grader checks ("a regression test fails if this line goes"), so a big win on it is only an upper bound for "if the right record reaches the agent". Read every child's arm prompt in its run script before citing its result.
6c. When the planned sandbox harness can't reach the model, a working fallback is one-shot agents `hermes -z "<task>" -m <model> --provider anthropic -t terminal,file --safe-mode` run with cwd in disposable `git worktree` checkouts, reset per run, scored with the same guard test; say in the report which harness ran.
6d. "Does the tool stop the agent breaking a recorded decision" (guard-test A/B): pick tasks where a plain agent actually breaks the decision. Pilot each candidate with the no-tool arm 2x and keep only those broken at least once; log the pilot as case selection and never score it. If most tasks are never broken in either arm, the A/B has no room to show an effect. Judge "task done" with a behaviour test or the captured diff, never a marker string: agents phrase a correct edit differently and the marker reads them as "didn't attempt". Capture every run's diff from run 1. If a running A/B turns out to have no headroom (the pilot breaks 0 of N and earlier scored runs broke only one task), stop it rather than spend hours measuring nothing: keep the finished rows as "stopped main run", then pre-register a narrow addendum (hash it before any new run) on only the tasks with a scored plain-agent break, with ~10 runs per arm and a Fisher exact test. Context handed over before the edit can change nothing (an agent broke a decision its context named, at the same rate as without it), so also test a closed-loop arm: check the diff after the agent finishes, hand failures back once, and score the final state.
6e. If the tool calls a model of its own (a router or judge inside a hook), a one-model frozen protocol can't include it silently. Run the tool arm with its model-free path in the frozen runs. Pre-register the tool-with-its-own-model arm separately, with its model calls and cost reported apart. Record the choice as a decision before run 1; the start command alone (an env flag) doesn't show it.
6f. Before scored run 1: re-hash every file in the freeze list and re-pin the product commit if it moved, writing the move into the freeze file header (no run has started, so this is not a protocol change). Confirm the model quota with one tiny call. While scored runs are going, start no other agents on the same subscription: a quota hit mid-run spoils that run, and parallel load inflates agent wall time.
6g. When the tool arm loses, separate retrieval from follow-through before redesigning. Regenerate the exact context the arm injected for each task (deterministic, no model, in a throwaway worktree) and count whether the scored decisions were named. If they were and the agent still broke them, the fix is the closed loop or the context shape, not retrieval. Report losses first, per task, and name tasks that score 0 in every arm as noise at n = 1. Expand to the pre-registered run count with nothing tuned in between; a design change after a loss is a new protocol version.
6g2. Run each arm from a PINNED COPY of the product (a detached worktree or extracted tarball at the frozen commit), never from the live working tree. Merges into main while epochs run change files the arm executes and break the freeze hashes. If it happened anyway: re-hash the freeze list, diff the changed files, and decide from the diff whether the executed path changed (e.g. an env override returns before the new code). Write that as a dated DEVIATION in the freeze file and the results, and keep the runs only if the executed code is the same. Also hold off rebuilding main's dist and running full checks until the last run finishes.
6g3. Score the full pre-registered run count with the protocol's own test (e.g. an exact paired permutation over task means, 2^n sign flips). Keep agent-error runs in as 0 (intention to treat), and report them plus the result without them. Report per-epoch numbers too: a first epoch that looked like a clear loss can level out, and the honest headline is then "no measurable gain, n.s.", not "the tool hurts". Update every public page that quoted the partial result in the same turn.
6g4. Audit the scorer before believing any arm difference: open-code every FAILED check across all arms (agent never touched the file · copied the deprecated pattern · ignored a shown decision · scorer artefact · task abandoned), then count per arm. A diff-based scorer that runs plain `git diff` never sees UNTRACKED new files, so every check whose evidence sits in a newly created file fails in all arms; run `git add --intent-to-add --all` before diffing (a disclosed deviation from the upstream scorer) and test that new-file content scores. Also grep the seeded repo for text that matches a fail regex by itself. Report pass^k (task passes all k epochs, tau-bench) beside the mean. Save every run's FULL diff (tracked + new files) in the run log from run 1, or a scorer bug found later can never be rescored.
6g5. Size the next protocol from the pilot's variance, never by copying the old run count: per-task paired-difference SDs into a power calculation (`statsmodels.stats.power.TTestPower().solve_power(effect_size=MDE/SD, alpha=.05, power=.8)`), shown in the spec's notes, then freeze. Say the resulting cost (runs x minutes) before starting it.
6g6. Build the reusable harness ON an established eval framework, not as scripts: Inspect AI Task + a solver that runs the external agent in a per-sample git worktree (the inspect-swe pattern), scorers wrapping the benchmark's own scorer, native `.eval` logs so `inspect view` works, statistics from scipy/statsmodels. The reviewer greps for the framework import and runs `inspect eval` + `inspect log dump`; prose-only "built on Inspect" is a FAIL. Per-sample resources (worktrees) are removed by the Task's `cleanup=` hook, which runs after scoring on success, error, timeout and cancel (a scorer `finally` never runs when the solver raises); sweep stale ones at task start. Give it an agent option users actually have (inspect-swe's claude_code/codex wrappers), not only the private harness, plus a 'does adding decision X change what my agent does' recipe on their own repo.
6h. Long scored runs outlive the machine: a reboot or sleep kills the runner with no exit line. When the run count stops moving, check the process and `last reboot`. Then remove the half-finished run's worktree and data dir (no record was written for it), prune worktrees, and restart the same resumable command: it skips run ids already in the output file. Log the interruption and the rerun run id in the results notes.
7. Pilot with 1 ticket x 2 conditions first: it finds harness bugs (stale answers, unreadable tool path, quoting of paths with spaces) for ~$0.15.

## Grading and reading
- Grade by F1 against the key; path-type tickets by verifying every edge against a graph. Then audit every ticket where ALL conditions miss the same file: that is a key or wording defect, not an agent defect (call-expression filters drop JSX renders and callbacks passed as arguments; "defined elsewhere" is ambiguous about same-file helpers). Fix the key or drop the ticket, and put the lenient scoring and the dropped-ticket subset INSIDE the grader output so the write-up numbers reproduce from the data file.
- Expect a ceiling: strong agents solve small-repo grep-friendly tickets in every condition, so correctness cannot separate them and fixed per-run cost (cached system prefix) swamps small tool effects (cost correlated ~0.96 with cache-write tokens). Say "not demonstrated", not "no-go", and name the alternatives: repo too small, tickets grep-friendly, "stop when confident" prompt suppressing exploration, tool index cost excluded, tool call capped output (a node cap forced grep fallback on list-all questions: a product finding).
- Ambiguity must be MEASURED, not assumed: "same function name declared twice" found zero candidates in a 674-file repo; the real noise is word-grep hits that are locals, properties or library methods, so rank candidate tickets by files a name-grep finds beyond the true callers and the definer. Tickets picked where the tool should help are favourable by design: say so next to every number.
- Before writing a saving into a claim, split it: the arm where the tool was OFFERED includes runs that never used it. If those non-users saved as much as users, the saving is not the tool. Also compare forced-use against baseline, take the ticket (not the run) as the unit for a sign test and a cluster bootstrap CI, and compare the effect with the baseline's own rep-to-rep difference. Keep only what survives every cut (here: one question type, small n) and withdraw the rest in every record, not just the chat.
- Read the agents' transcripts for what they say about the tool ("line numbers look stale"): it finds product bugs the grader cannot. Verify each against ground truth before filing it (a printed line was the caller's declaration, not the call site) and open a ledger task with a proof command.
- Disclose: cost is list-price estimate, isolation from the user's memory/instructions unprovable if the system prompt is not stored, no turn/budget cap, one model, one repo, CLI instead of MCP schema overhead.
- An independent reviewer reruns the grader to a scratch OUT path, recomputes medians in a second language, greps transcripts for reads outside the fixture, and checks stated numbers match the data file.
